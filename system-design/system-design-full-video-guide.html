2. Server overload: vertical vs horizontal scaling

Vertical

Bigger machine

More CPU and RAM. Same architecture, no code change. The video recommends this as the sensible first move when it solves the problem.

Cost: eventually there is a largest machine, and prices rise sharply.

Horizontal

More identical machines

Run several identical copies of the application. Each instance can serve any request.

Benefit: add more instances as traffic grows.

Why it works

Many apps are read-heavy. Writes stay on the primary while the much larger read workload is spread across replicas.

Replication lag

A replica can briefly be behind the primary. A user may create a post and immediately read from a replica that has not received it yet.

Selective correctness: ordinary feed reads can tolerate tiny lag; read-after-write experiences may deliberately read from the primary.

Good cache candidate

Follower count: expensive to compute repeatedly and a small amount of staleness is acceptable.

Bad cache candidate

Bank balance in the video's example: correctness is treated as more important than serving a stale cached value.

Cache invalidation

The moment you copy an answer into a cache, it can become stale. You must decide when to update, expire, or invalidate it.

Decoupling

Account creation no longer has to wait for an external email provider.

Eventual work

“Done” can mean the system accepted responsibility for the job, not that the background side effect has already completed.

Failure handling

Workers need retries; repeatedly failing jobs need somewhere to go for later inspection rather than silently disappearing.

9. Data no longer fits on one machine → Sharding

Replicas copy the entire database, so they do not solve a dataset that itself is too large for one machine.

→
Shard 3

String IDs

Hash the identifier into a stable number first, then apply the shard rule.

The trick

The same deterministic rule is used when writing and reading, so the app knows exactly which shard owns a user.

Cross-shard queries

Global counts, sorting, or searches may need to query every shard and combine the results.

Shard-key choice is architectural: choose well and common queries stay on one shard; choose badly and common operations fan out across every database. The video treats sharding as the last resort.

The engineering lesson

System design isn't knowing the boxes. It's knowing their order and their trade-offs.

Ask: What measured problem am I solving? Is there a simpler fix first? What new failure mode does this component create? Where can the product tolerate stale or eventual data, and where must it be immediately correct?
